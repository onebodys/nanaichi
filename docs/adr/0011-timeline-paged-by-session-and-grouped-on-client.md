# タイムラインはセッション単位でページを送り、日付の区切りと完了セット数は端末で計算する

`GET /api/timeline?before=<時刻>` は、開始時刻が `before` より前のセッションを新しい順に一定数（10件）返す。各セッションには操作イベント・記入の時刻（自動終了の判断用）・削除していない記入を含める。`before` を省けば、現在のセッションを含む最新のページになる。次のページの `before` は、そのページでいちばん古いセッションの開始時刻。

日付の区切りは端末のタイムゾーンの 0:00 なので（docs/PRODUCT.md）、サーバーではなく端末で決める。日付ごとの完了セット数も、セッションの操作イベントから端末で計算する（ADR 0003。完了セットは集中を終えた時刻の日付に数える）。サーバーにタイムゾーンを渡して数えさせる方法もあるが、操作イベントから状態を計算するのは画面がすでにしていることで、計算を二重に持たずに済む。進行中のセッションの完了セット数も、時刻が進めばそのまま増える。

記入ではなくセッションでページを送るのは、記入のないセッションの完了セットも数えるため。記入でページを送ると、記入のないセッションがタイムラインに現れず、その日の完了セット数が少なく出る。

## Consequences

- まだ読み込んでいない古いセッションがあるとき、読み込んだうちでいちばん古いセッションが始まった日は、その日の完了セット数が確定しない（その日の前半のセッションが次のページにあるかもしれない）。この日の区切りには完了セット数を出さず、続きを読み込んでから出す。それより新しい日は、セッションが重ならない（同時に1つまで）ので確定している。
- 1日に1ページ分（10件）より多くのセッションがあると、その日の完了セット数は続きを読み込むまで出ない。
- ネイティブアプリもタイムゾーンでの区切りを自分で計算する必要がある。計算はドメインの関数（`Timeline.build`）にあるので、Web では共有できる。

## Considered Options

- 記入単位でページを送る: 記入のないセッションの完了セットが数えられないため不採用
- サーバーがタイムゾーンを受け取り、日付ごとの完了セット数を返す: 計算を二重に持つことになり、進行中のセッションの数が時刻とともに増えるのを画面で再現できないため不採用
