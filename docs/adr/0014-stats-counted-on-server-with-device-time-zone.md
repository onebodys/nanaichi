# スタッツはサーバーが端末のタイムゾーンを受け取って数える

`GET /api/stats?period=<期間>&timeZone=<IANA のタイムゾーン>` は、そのユーザーのすべてのセッションと削除していない記入（本文を除く）を UserDO の SQLite から読み、ドメインの `Stats.of` で数えた結果を返す。日付と時間帯は、画面が送った端末のタイムゾーン（`Intl.DateTimeFormat().resolvedOptions().timeZone`）で区切る。ヘッダーの今日の集中時間も、この応答（期間は今日）の値を出す。

ADR 0011 では、日付ごとの完了セット数をサーバーで数える案を「計算を二重に持つ」「進行中のセッションの数が時刻とともに増えるのを画面で再現できない」ため退けた。スタッツではこの前提が変わる。

- 連続日数やこの12週間の集中、「すべて」の期間は、すべてのセッションを見ないと数えられない。タイムラインのようにページで少しずつ読み込む画面では、ページを全部読むまで数が出ない。
- タイムラインのページから数える今の作りでは、1日に10件より多くセッションがある日に今日の集中時間が出ない（ADR 0011 の Consequences）。

計算そのものは `domain/` の純粋な関数（`Stats.of`）にあるので、二重には持たない。サーバーはそれを呼ぶだけで、ネイティブアプリも同じ API を使える。

進行中のセッションの数は、画面がその変わり目で読み込み直して追いかける。画面は「今日の日付・現在のセッション・そのセッションの完了セット数・終了したか」の組を見ていて、これが変わったとき（集中を終えた・セッションを始めた／終えた・日付が変わった・他の端末で操作した）にだけ読み込み直す。完了セットが増えるのは集中を終えたときだけなので、ずれるのは応答が届くまでの間だけ。

## Consequences

- 1回の応答ですべての記録を読む。1人のユーザーの記録（1日に十数セッション、1年で数千セッション）なら DO の SQLite で十分速いが、遅くなったら日付ごとの集計を記録しておくなどの手当てを考える。
- タイムラインの日付の区切りは、引き続き端末が読み込んだページから数える（ADR 0011）。ただし今日の区切りが「数が確定しない」日になったときは、スタッツの今日の数を出す。今日より前の、数が確定しない日（読み込んだうちでいちばん古いセッションが始まった日）は、これまでどおり続きを読み込むまで出さない。
- 不正なタイムゾーンは 400 で断る。端末のタイムゾーンを変えれば、同じ記録でも日付の区切りが変わる。

## Considered Options

- 画面がすべてのセッションを読み込んで数える: 計算は今の `Timeline.build` に近いが、記録が増えるほど応答が大きくなり、スマホで重い。
- 日付ごとの集計を書き込み時に記録する: タイムゾーンが端末ごとに変わりうるのと、自動終了やフェーズの切り替わりが記録されない（ADR 0003）ため、書き込み時には日付が決められない。
