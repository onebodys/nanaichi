# 同期は UserDO からの WebSocket で、変わった記録そのものを配り、繋ぎ直したら読み込み直す

複数タブ・複数デバイスの同期（ADR 0002）は、`GET /api/ws` で WebSocket に切り替え、ユーザーの UserDO が Hibernation API で受け入れる。WebSocket はサーバーから画面への一方向にだけ使い、書き込み（開始・操作・記入）はこれまでどおり HTTP で送る。書き込みの応答で失敗（409 など）をそのまま返せ、ID による二重送信の防止（ADR 0007・0010）も HTTP のまま使えるため。

UserDO は記録を変えるたびに、そのユーザーのすべての接続へ同期メッセージ（GLOSSARY）を送る。メッセージには「変わった」という合図だけでなく、変わった記録そのもの（新しいスナップショット、書いた・編集した記入、削除した記入）を入れる。合図だけにすると、受け取った画面がそろって API を読みに来るうえ、受け取ってから反映するまでに1往復ぶん遅れるため。記入を書いたときは、自動終了の時刻が延びるので、記入とあわせて新しいスナップショットも送る。

切断している間のメッセージは届かない（取りこぼしを埋める仕組みは持たない）。代わりに画面は、接続するたびに（初回も繋ぎ直しも）スナップショットとタイムラインを読み込み直す。繋ぎ直しは間隔を延ばしながら（最大30秒）くり返す。スマホのスリープなどで切れたことに気づけないまま残る接続を見つけるため、画面は一定間隔で `ping` を送り、`pong` が返らなければ切って繋ぎ直す。`ping` には `setWebSocketAutoResponse` でランタイムが答えるので、UserDO は休止（hibernation）したままでよい。

## Consequences

- HTTP の応答と同期メッセージは、同じ変更について両方届くことも、順序が入れ替わって届くこともある。画面はスナップショットのサーバーの時刻を比べ、手元より古いものは捨てる（`SessionSnapshot.isOlder`）。記入は ID で置き換えるので、同じものが2回届いても困らない。
- 同期メッセージで届いたスナップショットでは時計のずれを測り直さない（送られた端末の時刻がわからない）。直前に HTTP で測ったずれを使う。
- 自動終了の alarm では同期メッセージを送らない。自動終了はどの画面も操作イベントと時刻から自分で計算している（ADR 0003）ので、知らせることがない。alarm のあとの記録は「セッションなし」になるため、送ると各画面の「自動終了しました」の表示が消えてしまう。
- 他の端末からの操作で状態が変わっても、フェーズの切り替わりとしては知らせない（人の操作で移ったときと同じ扱い。GLOSSARY の「フェーズの切り替わり」）。
- 接続を受け入れる前に、`Origin` がリクエストと同じ origin であることを確かめる。cookie で認証する WebSocket は CORS で守られないため（Cross-Site WebSocket Hijacking）。
- タグの削除だけは、書き換えた記入ではなく削除の操作（削除したタグと外し方）を送り、画面が手元の記入に当てる（ADR 0017）。

## Considered Options

- 書き込みも WebSocket で送る: 失敗の返し方と二重送信の防止を作り直すことになるため不採用
- 「変わった」という合図だけを配り、画面が読み込み直す: 全画面がそろって API を読みに来て、反映も1往復遅れるため不採用
- 切断中のメッセージを番号で取り直す: 繋ぎ直したときに読み込み直せば足り、記録の量も小さいため不採用
