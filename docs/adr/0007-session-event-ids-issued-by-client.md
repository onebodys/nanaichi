# 操作イベントの ID はクライアントが発行し、MVP では時刻をサーバーが受け付けた時刻で記録する

操作イベント（開始を含む）の ID は、送る側のクライアントが UUID で発行する。UserDO は同じ ID の操作が2回届いても1回分しか記録せず、2回目には1回目と同じ成功としてそのセッションの今の様子を返す。同じ ID で別の種類の操作が届いたら、クライアントの誤りとして 409（`EVENT_ID_CONFLICT`）で拒否する。これで通信のやり直しによる二重送信を防ぎ、将来オフラインで記録したイベントを後から同期するときも、同じ ID で重複を見分けられる（ADR 0003）。

一方、操作イベントの時刻は MVP ではサーバー（UserDO）が受け付けた時刻で記録する。MVP は Web のみでオンラインが前提なので、端末の時計のずれを持ち込まないことを優先した。クライアントはスナップショットのサーバー時刻との差で、表示する残り時間を補正する。

## Consequences

- オフライン同期を作るときは、クライアントが記録した時刻を受け付けるよう API を拡張する必要がある。そのとき、時刻の順が崩れたイベントのマージ方法も決める。
- 同じミリ秒に届いた操作は、記録した順に並べる（`session_events` の rowid）。

## Considered Options

- サーバーが ID を発行する: 二重送信を防ぐには別に冪等キーが要り、オフライン同期にも使えないため不採用
- MVP からクライアントの時刻を受け付ける: 端末の時計のずれで、記録上の時刻が前後しうるため見送り
