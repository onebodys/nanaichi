# ジャーナル記入の ID はクライアントが発行し、編集・削除はセッションの外でもでき、削除は論理削除にする

ジャーナル記入の ID は、操作イベントと同じく送る側のクライアントが UUID で発行する（ADR 0007）。UserDO は同じ ID の記入が2回届いても1件しか記録せず、2回目には記録済みの記入を返す。書いた時刻と紐付き（セッション・ラウンド・セット・フェーズ）は、サーバー（UserDO）が受け付けた時刻のタイマーの状態から決める。端末の時計のずれを持ち込まないためで、ADR 0007 と同じ理由。

記入を新しく書けるのはセッション中だけだが（ADR 0004）、書いた記入の編集・削除はセッションが終わったあとでもできる。タイムラインは過去の記録を振り返る場所を兼ねるので、書き間違いを後から直せないと不便なため。編集・削除は新しい記入を増やさないので、「セッションの外で書けるメモ帳にしない」という ADR 0004 の判断とは矛盾しない。編集しても書いた時刻と紐付きは変えない。

削除は論理削除（`deleted_at` を入れる）にする。削除した記入はタイムラインにも API の応答にも出さないが、自動終了の判断では書いたものとして数える。書いた時点で自動終了が先に延びたことは、後から削除しても変わらないため（変わると、過去のセッションの終了時刻が後から動いてしまう）。同じ理由で、編集は自動終了の判断に使う「最後の記入」に数えない。

## Consequences

- 記入の本文は PII なので、ドメインでは `Sensitive` に包んで持つ（AGENTS.md「境界での検証と PII」）。`Sensitive` は JSON にすると伏せ字になるため、API の応答は ADR 0009 の「ドメインの型をそのまま `c.json` で返す」の例外として、`JournalEntry.toJson` で本文を明示的に取り出した形にしてから返す。応答のスキーマ（`JournalEntryJsonSchema`）は本文を再び `Sensitive` に包む。
- 削除した記入の ID で書き直しや編集が届いたら、見つからないものとして 404（`JOURNAL_ENTRY_NOT_FOUND`）で拒否する。削除の再送は成功として扱う。

## Considered Options

- 編集・削除もセッション中に限る: 終わったセッションの書き間違いを直せず、振り返りの場として使いにくいため不採用
- 物理削除: 削除で自動終了の時刻が後から変わってしまうため不採用
