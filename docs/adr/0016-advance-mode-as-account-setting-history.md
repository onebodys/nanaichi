# フェーズの進め方はアカウントの設定の変更履歴として持ち、タイマーの計算に時刻つきで渡す

フェーズの進め方（GLOSSARY。Issue #42）は、4つの切り替わり（集中 → ジャーナル、ジャーナル → 集中、ジャーナル → 休憩、休憩 → 集中）ごとの自動・手動の組で、アカウントごとに1つ持つ。UserDO の SQLite に、変えた時刻と変えたあとの組を1行ずつ足していく（変更履歴）。いまの設定は最後の行で、行がなければすべて自動。

タイマーの状態は操作イベントと時刻から計算する（ADR 0003）。手動の切り替わりでは、時間が過ぎても次のフェーズが始まらず、切り替え待ちで止まる。止まっていた時間だけ後のフェーズがずれるので、どの時刻にどの進め方だったかがわからないと、過去のセッションの状態も完了セットの時刻も計算し直せない。そこで `deriveTimerState` に、操作イベントとジャーナル記入の時刻に加えて、進め方の変更履歴を渡す。計算は時刻の順に進め、フェーズが終わる時刻に効いている進め方で、自動で移るか切り替え待ちにするかを決める。

- セッションの途中で変えると、その時刻から効く。待っている切り替わりを自動に変えると、その時刻から次のフェーズが始まる（変えたのは人なので、フェーズの切り替わりとしては知らせない）。進めているフェーズの切り替わりを手動に変えると、そのフェーズが終わったときに切り替え待ちになる。
- 進め方の変更は、自動終了の判断では操作として数える（変えた人は画面の前にいる）。
- 切り替え待ちから次のフェーズを始める操作は、新しい操作イベント「進める（Advance）」として記録する。押した時刻から次のフェーズが始まる。ID はほかの操作と同じくクライアントが発行する（ADR 0007）。
- 切り替え待ちでできるのは、進める・終了と、休憩に入る前の切り替え待ちでの休憩スキップだけ。一時停止（もう止まっている）・中断（集中は最後まで終えていて完了セットになっている）・集中の再開始（待機のための操作）はできない。
- 自動終了は、これまでどおり最後の記入・操作から実際に過ぎた時間（58分）で数える。切り替え待ちの間も止め忘れでありうるので、時計を止めない。
- 複数の端末でほぼ同時に「進める」を押したときは、先に届いたほうだけを受け付け、後のほうは `OperationRejected`（409）になる。後から押した端末にも同期メッセージで新しいスナップショットが届き、画面は次のフェーズに追いつく。これは一時停止や再開を同時に押したときと同じ扱い。

スナップショットとタイムラインで送るセッション（`Session`）には、そのセッションの計算に要る変更だけを入れる。セッションを始めた時刻に効いていた変更（始める前の最後の変更）と、セッションの間（終了していれば終了まで）の変更。変えたら、新しい設定を同期メッセージ `AdvanceModeChanged` で、進行中のセッションがあれば新しいスナップショットも `SessionChanged` で送る（ADR 0012）。設定の読み書きは `GET /api/settings/advance-mode` と `PUT /api/settings/advance-mode`（ADR 0009）。

## Consequences

- 変更履歴は消さない。消すと、その変更をまたいだ過去のセッションの計算が変わってしまう。1回の変更で1行なので、量は問題にならない。
- 記録の上で閉じていないセッションを計算し直すときも、変更履歴の行を読む。セッションの行と操作イベントだけでは状態が決まらなくなった。
- 進め方を変えずに同じ組を送られたときは、行を足さない。
- 知らせ方の設定（音・音色・通知）は端末ごとのままで、これとは別に持つ。進め方はタイマーの状態そのものを変えるので、端末ごとに違うと端末によって残り時間が食い違ってしまう。

## Considered Options

- 進め方を開始の操作イベントに写しておき、セッションの途中では変えられない（次のセッションから効く）ようにする: 計算は簡単になるが、セッション中に設定画面で手動にしても何も起きず、変えたつもりの人を戸惑わせる。設定画面はタイマーに重ねて開く作り（Issue #34）で、セッション中に開くのが普通なので不採用。
- 進め方の変更を、進行中のセッションの操作イベントとして記録する: セッションの外で変えた分を別に持つ必要があり、同じ設定が2か所に分かれるので不採用。
- 切り替え待ちを一時停止として表す（時間が来たら自動で一時停止する）: 残り時間 0:00 の一時停止と、途中の一時停止の見分けがつかず、再開で何が起きるかも違う。待っている時間を「止めてから」と出すのも意味が違うので、別の状態にした。
- D1 に持つ: アカウントごとの値だが、タイマーの計算に毎回要り、セッションと同じトランザクションで読みたい。UserDO の SQLite に置く（ADR 0002 の「ユーザーごとのデータは DO」）。
