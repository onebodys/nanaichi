# この端末の記録は閉じたセッションごとにアカウントへ取り込み、時間が重なるものは端末に残す

ログインした人が、この端末の記録先（ADR 0019）に置いた記録をアカウントへ移すことを取り込み（GLOSSARY）と呼ぶ（Issue #106）。ログインすることは、有料プラン（お試しを含む）を使うことにあたるので（#110）、取り込みは無料から有料へ移る入り口になる。記録を失わないことと、途中で失敗しても同じ結果になることを、何より優先する。

## 流れ

- ログインした直後、この端末に閉じたセッションがあれば、セッションと記入の数を出して取り込むかを確かめる。「あとで」を選んでも、設定画面のアカウントの欄からいつでも取り込める。黙って取り込まないのは、別の人の端末で一時的にログインしたときなどに、記録が混ざるのを防ぐため。
- 取り込むのは閉じたセッションだけにする。セッションの途中では「ログインして同期」を押すと「セッションを終えてからログインしてください」と出し、ログインに進ませない。別のタブでログインしたなどの理由で開いたままのセッションが残っていれば、そのセッションは取り込みから外し、終わってから取り込めると知らせる（放っておいても自動終了で閉じる）。
- 束は閉じたセッションの記録（操作イベント、記入、削除した記入の印、終わった時刻と終わり方）を、この端末に保存しているのと同じ JSON の形式で送る。この形式は、期限切れのときにアカウントの記録をこの端末へ戻すとき（#112）にも使う。そのため、検証のスキーマは `device/` から `domain/` に移し、サーバーとこの端末の両方から使う（ADR 0009）。
- `POST /api/imports` に、セッションをいくつかずつ（件数と大きさの上限は実装で決める）順に送る。レート制限（ADR 0018）は10秒に100件なので、1件ずつは送れない。3年分（約9千セッション）でも百回ほどで送り終わる。429 が返ったら `Retry-After` だけ待って続ける。
- 応答はセッションごとに、受け取った（`Imported`）・すでにある（`AlreadyImported`）・時間が重なる（`Overlapping`）のどれかを返す。この端末は、受け取った分とすでにある分だけを、1つのトランザクションで消す。消すのは、サーバーが受け取ったと返したものだけにする（ADR 0019）。

## 同じ結果になること

- セッション・操作イベント・記入の ID は、すべて端末で発行している（ADR 0007、0010、0019）。アカウントにすでにある ID のセッションは `AlreadyImported` として受け取ったことにし、上書きしない。送ったあとで応答を受け取る前に通信が切れても、もう一度送れば同じ結果になる。
- 1つのセッションの取り込みは、UserDO の `transactionSync` の中で、全部書くか何も書かないかのどちらかにする。

## 時刻

- 端末の時刻で記録した時刻を、記録された時刻としてそのまま受け入れる。この端末の記録先には、それ以外の時刻がないため（ADR 0007、0010 の「サーバーが受け付けた時刻」の例外）。端末の時計のずれは、そのまま残る。

## 時間が重なるセッション

- 取り込むセッションの始めた時刻から終わった時刻までが、アカウントのどれかのセッション（開いているものを含む）と重なれば、取り込まずに `Overlapping` を返す。「同時に持てるセッションは1つまで」と、ADR 0011 の日付の数え方が、セッションが重ならないことを前提にしているため。
- 重なったセッションはこの端末に残し、「N件は時間が重なるため取り込めませんでした」と知らせる。設定画面から中身を確かめて捨てることもできる。ログアウトすれば、この端末の記録として見られる。
- 有料化すると、取り込みのほとんどは空のアカウントへの最初のログインになるので、重なることはまれと見込む。

## フェーズの進め方の履歴

フェーズの進め方の変更履歴（ADR 0016）は、セッションの状態の計算と、自動終了の判断（進め方の変更は操作として数える）に使う。端末の履歴をそのまま混ぜると、アカウントの過去のセッションの計算が変わってしまう。そこで、取り込むセッションごとに、次の行だけをアカウントの履歴に足す。

- そのセッションを始めた時刻に、端末でその時点に効いていた進め方の行。端末で変えた時刻のままにしないのは、その時刻にアカウントの別のセッションが進んでいたら、そのセッションの計算と自動終了の判断が変わってしまうため。
- セッションの間に端末で変えた行（時刻はそのまま）。
- アカウントに取り込み以外の記録がある場合だけ、セッションが終わった時刻に、取り込み以外の行から求めたアカウントのその時点の進め方に戻す行。

セッションが重ならない限り、アカウントのセッションの時間帯に効いている進め方は変わらない。

アカウントのいまの進め方は、アカウントに取り込み以外の記録（取り込んでいないセッション、または取り込みで足したのではない進め方の行）がなければ、端末のいまの進め方にする。あればアカウントの進め方のままにする。束を分けて送るので、2回目以降の束ではアカウントが空でなくなる。そのため、取り込みで足したセッションと進め方の行には印をつけ、「取り込み以外の記録があるか」で判断する。こうしておけば、途中で失敗してやり直しても判断が変わらない。

## タグ

- 合わせると20種類を超えても、取り込みでは断らない。使わないタグの削除（ADR 0017）を案内する。
- そのため、上限の判断を変える。いまの `Tag.ensureWithinLimit` は「使っているタグとつけるタグを合わせた種類が20を超えるか」を見ている。これだと、使っているタグがすでに20を超えているとき、タグをつけない記入まで書けなくなる。これからは、まだ使っていないタグをつけるときだけ、合わせた種類が20を超えないかを確かめる。使っているタグだけをつける記入は、いつでも書ける。

## Consequences

- アカウントのタイムライン・スタッツ・MCP サーバーに、取り込んだ記録が出る。数えるのはサーバーで、取り込んだかどうかで区別しない。
- UserDO の SQLite に、取り込みで足した行の印（セッションと進め方の変更履歴）を足すマイグレーションが要る。
- ジャーナル記入の本文が、初めて端末の外へ出る（ADR 0019 で予告したとおり）。送るのはログインしている本人のアカウントだけ。
- 取り込みを1件ずつではなく束にする専用のエンドポイントを足すので、ADR 0009 のとおり、応答のスキーマを `domain/` に、関数を `client/api.ts` に足し、結合テストで確かめる。
- 期限切れのアカウント（#110）では、取り込みは断る（アカウントに新しく記録できないため）。課金を入れるときに決める。

## Considered Options

- ログインしたら黙って取り込む: 手間はいちばん少ないが、別の人の端末でログインしたときにも混ざってしまうので不採用。
- 時間が重なっても取り込む: 「同時に持てるセッションは1つまで」を過去の記録に限って緩めることになり、日付の数え方とスタッツが二重に数えないかを見直す必要がある。まれなケースのために前提を崩すほどではないので不採用。
- 端末の進め方の履歴を、変えた時刻のまま全部混ぜる: アカウントの過去のセッションの計算と自動終了の判断が変わるので不採用（ADR 0016）。
- 進め方を、取り込むセッションの操作イベントとして写す: ADR 0016 が退けた「進め方を操作イベントとして持つ」と同じで、同じ設定が2か所に分かれるので不採用。
- 開いているセッションも取り込み、ログイン後のアカウントでそのまま続ける: 体験は良いが、取り込みの途中の操作と競合し、アカウント側にも開いたセッションがあるときの扱いが要る。セッションの途中でログインすることはまれなので、終えてからにした。
- 全部を1回のリクエストで送る: 3年分で約21 MiB になり、Workers のリクエストと DO の RPC の大きさの上限に近づく。途中で失敗したときに全部やり直しになるので不採用。
