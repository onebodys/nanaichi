# 判断モデルでジャーナルからタスクを自動で完了にする

ジャーナルに「ログイン画面のバグ修正が完了した」と書いたら、未完了のタスク「ログイン画面のバグ修正」が自動で完了になる。これを、小さく速い AI の判断モデル（Cloudflare Workers AI の clef-flash）でできるかを確かめる PoC を作る（Issue #120）。ドッグフーディングの参加者が本番でそのまま試せる最小の形にする。

- **タスク**（GLOSSARY）: ログインしているとき（記録先がアカウント）だけの機能。タイトルだけを持つ未完了 / 完了の2状態で、ユーザーが足し、タイトルの変更・完了・再開・削除ができる。UserDO の SQLite（`tasks`）に置き、同期メッセージ（`TaskSaved` / `TaskDeleted`）で開いている画面に届ける。この端末の記録先（ADR 0019）には持たない。
- **ジャーナルからの完了**（GLOSSARY）: ジャーナル記入を書いたあとに、判断モデルが未完了のタスクごとに「その記入がやり終えたことをはっきり述べているか」を確率で答える。**確率が 0.9 以上のタスクだけを自動で完了にする**。届かないものは何もせず、提案の画面も出さない。完了にしたタスクには、もとの記入と確率を残し、画面に「ジャーナルから完了 (96%)」と出す。
- **使うかどうかはアカウントの設定で決める**（ADR 0027）。既定は無効で、無効の間はパネルを出さず判断モデルも呼ばない。
- **タスクは自動では作らない**。「追加すべきタスク」の自動判定は PoC の範囲外。
- **判断は記入の応答を待たせない**。`UserDO.writeJournalEntry` が記入を書いたあとに `ctx.waitUntil` で判断を始める。UserDO の書き込みは同期のトランザクション（`transactionSync`）なので、判断を「用意（未完了のタスクを読み、上限を確かめ、判断を始めたと記録）」と「記録（答えから完了にするタスクを決めて保存）」の2つの同期的なワークフローに分け、間の非同期な呼び出しだけを UserDO（Imperative Shell）が行う。判断が失敗しても、記入には影響しない。
- 質問は記入1件につき1回の呼び出しで、未完了のタスク（多いときは新しいものから20件）ごとに `noul` の質問を1つ作る。本文は 2000 文字までに切る。入力のトークンは実測で「約70 + タスク1件につき約120 + 本文1文字につき約0.5」で、本文はタスクの数に関わらず1回分しか数えられない。20件と2000文字で1回あたり約3,500トークン（約12ニューロン）、1日200回をすべてこの条件で使うと約2,400ニューロンで、無料枠（1日10,000）の約4分の1になる。タスクを60件渡すと1回で約7,400トークンになり、同じタスクを並べた試しでは確率が0.25から0.93にばらついたので、件数を絞る。手元の試しでは、「〜が完了した」「〜終わった」と書いたものは 0.94 から 0.96、関係のないタスクは 0.01 から 0.08 だった。
- 答え（しきい値に届かなかった惜しいものを含む）は `task_judgments` に、判断の回数・使ったトークン・結果は `task_decision_runs` に残す。PoC の評価でしきい値や質問を見直せるようにするため。

## 費用を使わないための決まり

- 判断モデルを呼ばない場合を先に決める: 未完了のタスクがなければ呼ばない。記入ごとの判断は1回だけ（再送では呼ばない）。1人あたり UTC の1日に 200 回まで（`DAILY_DECISION_LIMIT`、`task_decision_runs` を数える）。
- Cloudflare の Workers Free（1日 10,000 ニューロン）を超えると呼び出しがエラーになり、課金はされない。エラーは「判断モデルが使えない」として扱い、記入にもタスクにも何もしない（失敗側に倒す）。
- AI のバインディングはローカルでも本物の Workers AI につながる（ローカルの代用品がない）。そこで、開発サーバー（`vite.config.ts` の `remoteBindings`）とテスト（`vitest.workers.config.ts` の `remoteBindings: false`）では既定でつながない。つながないバインディングは「リモートで動かす必要がある」と失敗するだけで、判断モデルは使えない扱いになる。開発サーバーで本物を試したいときだけ `NANAICHI_REMOTE_AI=enabled` を明示する（`docs/SETUP.md`）。E2E（CI には Cloudflare のログインがない）は `e2e.config.ts` が `disabled` を渡す。
- テストは、UserDO の判断モデルを `replaceTaskJudge` で偽物に差し替えて確かめる。本物の Workers AI を呼ぶテストは作らない。
- PR のプレビュー（ADR 0025）の Worker にはバインディングを足さない。`wrangler-config.test.ts` がそれを確かめる。

## Consequences

- ジャーナル記入の本文（PII）が Workers AI に送られる。Workers AI はユーザーのデータを学習に使わず保持しない（zero data retention）サービスとして使う。本文は 2000 文字までで、ログには出さない。
- 判断モデルが使えなかった記入は、あとから判断し直さない。判断は記入1件につき1回で、`task_decision_runs` に残る。PoC の間は、取りこぼしより費用が出ないことを優先する。
- 確率 0.9 は PoC の手元の試しだけで決めた値。誤って完了にしたときは、画面でタスクを再開できる。`task_judgments` の惜しい答えを見て、値を見直す。
- タスクの削除は物理削除。タスクを消しても `task_judgments` の答えは残る。
- UserDO のスキーマにマイグレーション（`tasks` / `task_decision_runs` / `task_judgments`）が増える。
- 判断モデルが入力のトークンを返すので、`task_decision_runs.input_tokens` で利用量を見られる。無料枠に収まるかはこの値で確かめる。

## Considered Options

- 大きな LLM（テキスト生成）に判断させる: 遅く、記入のたびに費用が出る。確率でなく文章で返るので、しきい値で自動適用するには別の解析が要る。clef-flash は質問ごとの確率を速く安く返すので、「確率が高いときだけ自動で適用する」に合う。
- 提案の画面を出して、人が承認する: 誤りが少なくなるが、PoC の問いは「自動で完了にできるか」なので、まず自動の精度を見る。0.9 未満は何もしないことで、誤って完了にするのを抑える。
- 記入を書く応答のなかで判断する: 判断モデルが遅いと記入の応答が遅くなり、失敗が記入の失敗になりうる。書いたあとに `waitUntil` で行う。
- クライアント（ブラウザ）から判断モデルを呼ぶ: API の鍵がなくても動くが、本文をブラウザから直接外へ出すことになり、上限の回数も数えられない。サーバーから呼ぶ。
- Queues や Workflows で判断をキューに入れる: 取りこぼしをなくせるが、PoC には重い。`waitUntil` で足りる。
