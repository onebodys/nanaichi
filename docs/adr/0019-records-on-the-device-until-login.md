# ログインしていなければ記録をこの端末に置き、同じワークフローをブラウザで動かす

ログインしなくても、同期以外のすべて（タイマー、ジャーナル記入、タグとタグの削除、スタッツ、ジャーナルのカレンダー、フェーズの進め方）を使えるようにする（Issue #85）。ログインしていない人の記録は、そのブラウザの IndexedDB に置く。ログインすると、端末間の同期と MCP サーバーが使えるようになる。ログインしていない人が `/` を開くと、ログイン画面を挟まずにこの端末の記録でタイマーが動く。

記録をどこに置くかを記録先（GLOSSARY）と呼び、この端末とアカウントの2つがある。記録先は、ページを読み込んだときに Better Auth のセッションの有無で1回だけ決める。ログインは Google へのリダイレクト、ログアウトは `/` への移動で、どちらもページを読み込み直す。なので、開いている画面の下で記録先が入れ替わることはない。セッションの確認が通信の失敗で終わったときは、この端末の記録先に切り替えずに、読み込み直しの画面を出す。ログインしている人の記録が2か所に分かれるのを防ぐため。

## 画面は記録先を知らない

画面とフックは `client/backend.ts` の `Backend` だけを使う。`Backend` は、いまの `client/api.ts` の呼び出しと同じものに、同期メッセージを受け取る `subscribe` を足したもの。実装は2つある。

- アカウント: いまの HTTP の API と WebSocket（UserDO）。
- この端末: `device/` が UserDO と同じワークフローを、この端末の記録につないで動かす。

失敗は `BackendError`（`Unreachable`・`Rejected`・`StorageFailed`・`Broken`）で返し、HTTP のステータスは含めない。`Rejected` の `code` は、どちらの記録先でも同じ `ApiErrorCode`。ワークフローのエラーからコードへの対応は `workflows/rejection-code.ts` の1か所に置き、サーバーとこの端末の両方が使う。書き込みのあとにどの同期メッセージを送るかも `workflows/user-commands.ts` の1か所に置く。2つの記録先で同じ操作の結果や知らせが食い違わないようにするため。

ログインしているかどうかを読むのは、ヘッダーと設定画面のアカウントの欄だけにする。データを扱うフック（`client/use-*.ts`）が `useRecordStore` を import すると、Oxlint の `no-restricted-imports` で落ちる。

## この端末の記録

- 記録はメモリの上では1つの不変の値（`DeviceRecords`）にまとめる。開いているセッションは「なし」か「1つ」のどちらかの型で持ち、2つ開くことはできない。操作イベントは記録した順に並べ、同じミリ秒の操作の順序は配列の順で決まる（SQLite の `rowid` の代わり）。削除した記入も、書いた時刻とセッションを残す。自動終了の判断では、削除した記入も数えるため。終了したセッションは、終了した時刻と終わり方だけを残し、タイマーの状態はドメインで計算し直す（UserDO の SQLite と同じ）。
- IndexedDB には、セッションごとに1件（そのセッションの操作イベントと記入を含む）と、フェーズの進め方の履歴などをまとめた1件に分けて保存する。書き込みでは、変わったセッションの分だけを1つのトランザクションで書く。文書を丸ごと書き換えると、3年分（約9千セッション、約5.7万件の記入を合成したもの）で約21 MiB になり、書き込みのたびに数百ミリ秒かかったため（Node で測った値）。ワークフローの途中で例外が出たら何も書かない。UserDO の `transactionSync` と同じく、タグの削除で記入を何件書き換えても、全部書くか何も書かないかのどちらかになる。
- ジャーナル記入の本文は `Sensitive` で包まれているため、`JSON.stringify` すると `"[REDACTED]"` になって本文が消える。保存は `JournalEntry.toJson` を通し、読み込みは `JournalEntryJsonSchema` で検証して `Sensitive` に包み直す。
- 読み込めない文書（壊れている、または新しい版のアプリが書いた）は上書きしない。生の値を退避用のキーに写してから、`Broken` または `StorageFailed` を返す。この端末にしかない記録を、アプリの不具合で消さないため。
- 複数のタブで同時に開いても、`navigator.locks` で一度に1つのタブだけが読み書きする。2つのタブで同時に開始しても、開くセッションは1つ。書いたあとは、UserDO が送るのと同じ同期メッセージを `BroadcastChannel` で書いたタブを含むすべてのタブへ送る。
- 時刻は端末の時刻で記録する。ただし、記録済みのいちばん新しい時刻より前には戻さない。端末の時計は時刻合わせや手での変更で戻ることがあり、戻った時刻で操作するとドメインが「記録済みのイベントより前」として例外を出し、どの操作もできなくなるため。スナップショットのサーバーの時刻も端末の時刻になるので、時計のずれはほぼ 0 になる。セッションの ID も端末で発行する。
- 自動終了のための alarm はない。ワークフローが読み込むたびに、自動終了の時刻を過ぎたセッションを閉じる（`loadOpenSession`）。
- 最初に書くときに `navigator.storage.persist()` を求める。Safari は、しばらく開かれなかったサイトの保存領域を消すことがあるため（WebKit の公開している方針による推測で、実際には確かめていない）。

## 依存の向き

`device/` は新しい Imperative Shell で、`domain/` と `workflows/` を import してよい。`client/`・`server/`・React・Hono・`cloudflare:*` は import しない。`client/` は `device/index.ts` だけを import してよく、`workflows/` と `server/` はこれまでどおり import しない。ワークフローをブラウザで動かすのは `device/` だけになる。どれも Oxlint の `no-restricted-imports` で検査する（AGENTS.md の3章）。ログインしている人がワークフローの分までダウンロードしないよう、`device/` は動的 import で読み込む。

## Consequences

- 2つの記録先が同じ振る舞いをすることは、同じ場面の一覧を SQLite のアダプタとこの端末の記録の両方に通すテストで確かめる。片方の実装を読んで確かめるのではない。
- ADR 0002 の「ユーザーごとのデータは DO」は、ログインしている人に限った話になる。ADR 0007 と 0010 の「時刻はサーバーが受け付けた時刻」も、この端末の記録先では端末の時刻になる。ADR 0014 のスタッツは、記録を持っている側（サーバーか、この端末）が数える。ADR 0016 のフェーズの進め方は記録先ごとに持ち、この端末ではブラウザごとになる。ADR 0018 の「`/` は、未ログインならログイン画面へ」は、この端末のタイマーに変わる。
- ジャーナル記入の本文は、ブラウザの中に平文で残る。本文を端末の外へ送ることはない（ログイン時の取り込みを除く）。そのぶん、XSS で読まれないことの重みが増す。
- この端末の記録はログインしても消さない。取り込みが終わるまで、ログアウトすると `/` にこの端末の記録がまた出る。
- ログイン時の取り込みは、別の ADR と PR で決める。重なるセッション、合わせて20種類を超えるタグ、アカウントの過去のセッションを変えてしまうフェーズの進め方の履歴の扱い、一括で送るためのエンドポイントを決める必要がある。この ADR では、取り込みを何度やり直しても同じ結果になるよう、ID をすべて端末で発行し、元の時刻と削除した記入の印を残しておく。

## Considered Options

- localStorage に1つのキーで置く: 読み書きが同期なのでワークフローの契約にそのまま合う。しかし容量の上限が約500万文字で、ヘビーに使うと約1.4年で届く（記入1件を約400文字、1日16件として見積もった。測ったものではない）。どちらにしてもタブ間のロックの中で非同期に読むので、IndexedDB にしても増えるのは読み込み1回だけ。
- IndexedDB に1つの文書として置き、書き込みのたびに丸ごと書き換える: 原子性は簡単に得られるが、上に書いたとおり記録が増えると書き込みが遅くなるので不採用。
- 画面のフックでログインしているかどうかを見て分岐する: すべてのフックが記録先を知ることになり、これから書くフックも同じ分岐を書き写すことになるので不採用。
- Service Worker で `/api/*` をブラウザの中で答える: フックは変わらないが、サーバーのコード（Hono・認証・DO の RPC）がブラウザに入り、確かめるのも不具合を追うのもいちばん難しい場所に処理が隠れるので不採用。
- ドメインの関数を直接呼ぶ（LP のお試しと同じ）: lint の変更は要らないが、18本のワークフローの検証・再送の扱い・断る判断を書き直すことになり、2つの記録先がずれていくので不採用。
- タブごとに記録を持ち、読むときに合わせる: 開いているセッションは1つという約束がタブをまたぐので、2つのタブがそれぞれ開始できてしまい不採用。
- `client/local/` に置き、lint の例外で `workflows/` を許す: Oxlint の `overrides` は、あとに書いたものが前の規則を丸ごと置き換える。例外の側で `server/` や React の禁止を書き直し忘れると、黙って外れてしまう。最上位の `device/` にして、ディレクトリごとに1つの規則にした。
