# テスト用のログインは、バインディングとホストの両方がそろったローカルの開発サーバーでだけ開く

E2E のテストと、ワーカーが画面をブラウザで確かめる作業のために、Google を通さずにログイン済みのセッションを作る経路 `GET /api/test/sign-in?email=...` を用意する。中身は API のテストの土台と同じく Better Auth 公式の `testUtils` で、本番の設定（`auth.ts`）とは別のインスタンスに入れ、D1 と secret だけを共有する（`server/test-auth.ts`）。許可リストに載っていないメールアドレスではログインさせない。

この経路は、次の両方がそろったときだけ開き、それ以外では経路がないものとして 404 を返す。

- バインディング `TEST_SIGN_IN` が `enabled`。`.dev.vars`（デプロイされない）と `e2e.config.ts` でだけ渡し、`wrangler.jsonc` の `vars` や `wrangler secret` には登録しない
- リクエストのホストがローカルの開発サーバー（`localhost:5173` / `127.0.0.1:5173`、または portless が割り振る `*.localhost`）

`*.localhost` は Issue #43 で足した。worktree ごとに `vp dev` を立てるとポートがぶつかるので、[portless](https://portless.sh/) で `http://<ブランチ>.nanaichi.localhost:1355` のように名前で分ける。このホストは Google のリダイレクト URI にワイルドカードで登録できず Google のログインが通らないため、人間もテスト用のログインでログインする（ログイン画面には開発サーバーでだけ入口のフォームを出す。`import.meta.env.DEV` で分けるので本番のビルドには入らない）。`.localhost` は RFC 6761 でループバックに予約された名前で、ブラウザは必ず手元のマシンに解決するので、本番のホストになることはない。ポートは portless の設定で変わるので問わない。

片方だけでは本番で開かないことを保証しきれない。バインディングだけだと、誤って `wrangler secret put TEST_SIGN_IN` すれば本番で誰でもログインできてしまう。ホストだけだと、ローカルの開発サーバーで誰でも任意の許可済みユーザーになれる状態がいつもできてしまう。両方を要求すれば、本番のホストではバインディングに関わらず開かない。

## Consequences

- 本番で開かないことはテストで確かめる。`test-sign-in.test.ts` はバインディングがないとき・`enabled` 以外のとき・本番のホストのときに 404 になることを、`test-sign-in.workers.test.ts` は `wrangler.jsonc` のとおりに起動した Worker（本番と同じバインディング）で 404 になることを確かめる。`wrangler.jsonc` に `TEST_SIGN_IN` を書き足すとこのテストが落ちる。
- 経路のコードと `testUtils` は本番のバンドルにも入る。ビルド時に取り除く方式（`import.meta.env.DEV` など）より、実際に動く Worker の振る舞いをテストで確かめられることを優先した。
- 状態を変える操作を GET にしている。ブラウザで URL を開くだけで（E2E の `app.open` や agent-browser の `open` で）ログインできるようにするため。ローカルの開発サーバーでしか開かないので、他のサイトから踏ませてもテスト用のユーザーでログインさせられるだけで、守るべきものがない。

## Considered Options

- portless のホストで本物の Google ログインを通すために Better Auth の `oAuthProxy` を使う: 固定の callback URL で受けて元の URL へ戻せるが、受け口として常に動くサーバー（実質は本番）と secret を共有することになり、ローカル開発のために本番との結びつきを強めるので不採用（Issue #43）

- E2E でだけ Google のモックサーバーを立てる: 本物のログインの流れを通せるが、OAuth の画面と callback をモックする手間が大きく、ワーカーが手元で画面を確かめる用途には重いため不採用
- メールとパスワードのログインを開発時だけ有効にする: 本番の Better Auth の設定を環境で分岐させることになり、本番で有効になっていないことを確かめにくいため不採用
- バインディングだけで開閉する: secret の登録ミスで本番に開いてしまうため不採用
