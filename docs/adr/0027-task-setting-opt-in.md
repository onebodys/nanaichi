# ToDo はアカウントの設定で有効にしたときだけ使う

ToDo（タスクとジャーナルからの完了、ADR 0026）は、ログインしている全員に出していた。判断モデルを呼ぶと費用が出るので、使うと決めた人だけに絞る（Issue #120）。ログインしている（有料会員にあたる）うえで、設定の「ToDo を使う」をオンにした人だけが使える。既定はオフ。

- **ToDo の設定**（GLOSSARY）は `Enabled | Disabled` の判別可能な union（`domain/task-setting.ts`）。ブール値にしない。
- **アカウントの設定として UserDO に置く**。サーバーが「判断モデルを呼ぶか」を知る必要があるため、端末ごとの設定にはできない。どの端末でも同じで、変えると同期メッセージ `TaskSettingChanged` で開いている画面に届く。置き場所は現在の値だけを持つ1行の `task_setting` テーブル（行がなければ無効）。フェーズの進め方（ADR 0016）と違い、時刻ごとの履歴は要らない。
- API は `GET` / `PUT /api/settings/tasks`。本文は設定そのもの（`{ "kind": "Enabled" }`）で、valibot で検証する。いまと同じ設定への `PUT` は何も記録せず、同期メッセージも送らない。
- **無効なら判断モデルを呼ばない**。`prepareCompletionFromJournal` が最初に設定を確かめ、無効なら `TasksDisabled` で見送る。タスクも判断の回数も読まず、判断を始めたとも記録しない。
- **無効のときに止めるのは画面と判断モデルだけ**。ホームは ToDo のパネルを描かない。タスクの API（`/api/tasks`）は無効でも呼べるままにして、拒否は足さない（変更を小さくするため。画面から作れないものを API だけが受ける状態は許す）。作ったタスクは消さず、有効に戻すとまた出る。
- 設定画面の「ToDo」の項目は、アカウントの記録先でだけ出す。この端末の記録先は ToDo 自体を使えないので、案内も出さない。

## Consequences

- 既存の利用者は、設定をオンにするまでパネルが消える。オンにすれば、残っているタスクがそのまま出る。
- 無効の間に記入した内容は、あとで有効にしても判断しない（判断は記入1件につき1回、書いたときだけ）。
- UserDO のスキーマにマイグレーション（`task_setting`）が増える。
- パネルをタイマー側へ移して作り直す話は、この決定の外（あとで行う）。

## Considered Options

- 端末ごとの設定（ブラウザの localStorage）: サーバーが判断モデルを呼ぶかを知れず、費用を止められない。
- フェーズの進め方と同じ変更履歴の表: 設定の時刻を引く用途がなく、過剰。
- 無効なときはタスクの API も 403 で拒否する: 一貫するが、変更が大きくなる。まず画面と費用だけを止める。
