# タグの削除は記入のタグの書き換えとし、同期では削除の操作そのものを配る

タグの削除（GLOSSARY、Issue #84）は、タグの表を作らないまま（ADR 0013）、そのタグがついている削除していない記入すべてについて、`journal_entry_tags` を書き換えることとする。外すだけならその名前の行を消し、付け替えるなら付け替え先の名前に置き換える。付け替え先がすでについている記入では、先にあった位置の1つにまとめる。外し方・まとめ方は `DeletedTag.applyTo` という純粋な関数1つにし、UserDO の記録にも画面の手元の記入にも同じ関数を使う。

付け替え先は使っているタグに限る。名前の変更（新しい名前への付け替え）は今は要らず、使っているタグに限ればタグの種類が増えないので、上限（20種類）を確かめなくてよい。

記入を編集するのではないので、記入の更新時刻（`updatedAt`）は変えない。変えると、タグを1つ削除しただけで、そのタグがついていた記入がすべて「編集済み」と出てしまうため。

同期メッセージ（ADR 0012）は、書き換えた記入を1件ずつ送るのではなく、削除したタグと外し方（`TagDeleted`）を1つ送る。画面は読み込んだ記入に同じ `DeletedTag.applyTo` を当てる。ADR 0012 は「変わった記録そのもの」を送ると決めたが、タグの削除は何百件もの記入を一度に変えうるため、記入を送るとメッセージが大きくなり、本文（PII）も毎回送ることになる。削除の操作は時刻にも記入ごとの状態にもよらず決まるので、画面が自分で当てても記録と食い違わない。同じ削除を2回当てても結果は変わらない（削除したタグはもうないので何もしない）ので、HTTP の応答と同期メッセージの両方で当ててよい。

## Consequences

- 画面が読み込んでいない古いページの記入は、あとで読み込んだときに書き換え済みのものが届く。
- 入力欄でつけたままのタグ（端末ごとの localStorage、ADR 0013）からも、削除を受け取った画面で同じように外す（付け替える）。そのまま続けて書くと、削除したタグがまた記入につき、使っているタグに戻ってしまうため。削除したときに閉じていた端末には届かないので、その端末でつけたままのタグは残る（書けばまたタグとして使われる）。
- 削除するタグが使われていなければ `TAG_NOT_FOUND`（404）を返す。通信のやり直しで2回目の削除が届いたときもこれになるが、画面は一覧を読み込み直せばよい。
- タグごとの完了セット（スタッツ）は記入のタグから数えるので、削除・付け替えのあとに読み込めば反映される。

## Considered Options

- タグの表を作り、削除をその行の削除にする: ADR 0013 のとおり、名前のほかに持つものがないため不採用
- 書き換えた記入を `JournalEntrySaved` で1件ずつ送る: 件数が多いとメッセージが大きくなり、本文も送ることになるため不採用
- 「変わった」とだけ送り、画面がタイムラインを読み込み直す: ADR 0012 と同じ理由（全画面がそろって読みに来る、反映が1往復遅れる）に加え、古いページまで読み込み直す仕組みが要るため不採用
- 削除で記入の更新時刻を進める: 「編集済み」が大量に出て、本人が書き直した記入と見分けられなくなるため不採用
