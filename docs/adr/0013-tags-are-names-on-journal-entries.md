# タグは記入についた名前として持ち、独立した実体を作らない

タグ（GLOSSARY）は、ジャーナル記入ごとにつけた名前の並びとして記録する（UserDO の SQLite の `journal_entry_tags`）。タグそのものの表（作成日時・色・説明などを持つ実体）は作らない。どの記入にもついていないタグは存在せず、使えるタグの上限（20種類）も「削除していない記入についているタグの種類」で数える。

タグに名前以外に持たせたいものが今はなく、実体を作ると「どの記入にも使われていないタグ」を消す・名前を変える画面が要るため。記入を削除したり編集で外したりすれば、使っていないタグは自然に消え、上限の枠も空く。入力の候補（使ったことのあるタグを最近使った順）も記入から計算できる。

名前は入力を NFKC で正規化し、英字を小文字にしてから記録する（先頭の `#` は外す）。`#Reading` と `#reading`、全角の `＃ｒｅａｄｉｎｇ` を同じタグとして数えるため。ひらがなとカタカナは寄せない。記録した名前はすでに正規化されているので、正規化の規則を後から変えるときは記録を書き直す必要がある。

入力欄でつけたまま続けて書く記入にもつくタグは、端末（localStorage）に覚え、サーバーには送らない。端末ごとに書くことは違いうるうえ、サーバーに持つと同期メッセージとセッションの記録を増やすことになるため。セッションの外でつけたタグは「準備したタグ」として覚え、次に始めたセッションを画面が見つけたら、そのセッションの ID と一緒に覚え直す。セッションの ID が変われば（そのセッションが終わった）、つけたままのタグは外れる。記入と違い、タグをつけるのはセッションの外でもよい（開始前に「これをやる」と準備してから始める使い方のため）。

## Consequences

- タグを数える・タグで記入を探す（Issue #31 で後回しにした集計）は、`journal_entry_tags` を名前で引けばよい。名前の索引を張ってある。
- 上限は書く・編集するときに UserDO が判断する（`Tag.ensureWithinLimit`）。画面も同じ関数で、新しく作れるかを先に判断して知らせる。
- 削除した記入のタグは上限にも候補にも数えない。削除した記入は戻せないので困らない。
- 使わないタグを消す画面は、のちに Issue #84 で作った。実体は作らず、タグがついている記入すべてのタグを書き換える（ADR 0017）。
- タグの名前は PII として `Sensitive` に包まない。記入の本文と違って短い分類の名前で、入力の候補として画面に並べ、API でもそのまま返すため。検証エラーの応答には、これまでどおり不正な項目の位置しか出さない。

## Considered Options

- タグの表を作り、記入から ID で参照する: 名前のほかに持つものがなく、使われなくなったタグを消す画面が要るため不採用
- 本文の中の `#読書` をタグとして読み取る: Issue #31 でタグの欄を本文と分け、続けて書く記入にもつけたままにする仕様のため不採用
- つけたままのタグをサーバーに持ち全端末で揃える: 同期の仕組みが大きくなるため不採用（Issue #31 で端末ごとと決めた）
