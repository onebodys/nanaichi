# スナップショットの新旧は、サーバーの時刻ではなく記録先が進める変更の番号で決める

ADR 0012 では、同じ変更が HTTP の応答と同期メッセージの両方で届き、順序が入れ替わることがあるので、画面はスナップショットのサーバーの時刻を比べて手元より古いものを捨てると決めた（`SessionSnapshot.isOlder`）。その前提は「同じサーバーの時刻なら同じ変更」だった。

この前提は成り立たない（Issue #51）。Workers の時計は I/O まで進まないので、同時に届いた2つの要求は同じミリ秒に処理されうる。繋ぎ直しの読み込みと別の画面の開始が同じミリ秒 T に処理されると、開始の前の読み込みと開始のあとのスナップショットが同じ T を持つ。同期メッセージのあとに読み込みの応答が届くと、時刻が同じなので古いとみなされず、画面は開始の前に戻る。画面が1つでも、読み込み直しと記入が同じミリ秒になれば起きる。TLA+ のモデル（`formal/session-sync`）と、本物の UserDO を動かしたトレースの両方で確かめた。

そこで、スナップショットに**変更の番号**（GLOSSARY）を持たせ、新旧をそれで決める。

- 記録先は、スナップショットに入る記録（セッション、操作イベント、ジャーナル記入、フェーズの進め方の変更）を変えるたびに番号を進める。番号は減らない。何も記録していない記録先は 0。
- スナップショットは、作ったときの番号を `revision` に持つ（`NoSession` も持つ）。ワークフローは記録を書いたあとに `CurrentRevision` で番号を読んで、スナップショットに入れる。
- `isOlder` は、番号が手元より小さければ古いとする。同じ番号なら同じ記録から作ったものなので、サーバーの時刻が手元より前のものだけを古いとする。番号が大きければ、サーバーの時刻が前でも新しい。

## 記録先ごとの進め方

- UserDO（DO の SQLite）と Mac アプリの端末の記録先（SQLite、ADR 0028）: 1行だけの表 `record_revision` を、セッション・操作イベント・記入・進め方の変更の表の INSERT / UPDATE / DELETE のトリガーで進める。書き込みの経路を足しても進め忘れない。1つの書き込みで複数の行を変えればその数だけ進むが、使うのは「減らない」と「変更の前と後で違う」ことだけ。
- Web のこの端末の記録先（IndexedDB、ADR 0019）: 保存先がもともと書き込むたびに進める版（`VaultContent.revision`）を使う。1回の読み書きのサイクルで記録を変えていれば、読み込んだときの版に 1 を足した値にする。保存したあとの版はそれ以上なので、次のサイクルの番号は必ずそれ以上になる。

番号は記録先ごとのもので、記録先をまたいでは比べない。取り込み（ADR 0020）で行を写しても番号は写さない（アカウントの番号は、取り込んだ行のトリガーで進む）。ログインして記録先が変われば、画面は読み込み直す。

## Consequences

- ADR 0012 の「画面はスナップショットのサーバーの時刻を比べ、手元より古いものは捨てる」を、この ADR で置き換える。同期のしくみ（WebSocket で変わった記録を配り、繋がるたびに読み込み直す）は変えない。
- サーバーの時刻は、時計のずれを測るためだけに使う（ADR 0003）。
- API のスナップショットの応答と `SessionChanged` に `revision` が増える。画面とネイティブアプリは `revision` のない応答を受け付けない（Worker は画面と一緒に配信するので、古いサーバーと新しい画面の組はない。ネイティブアプリは新しいサーバーの応答の余分な項目を読み飛ばす）。
- 自動終了の alarm がセッションを閉じても番号は進む（行を変えるため）。同期メッセージは今までどおり送らない（ADR 0012）。
- 操作と重なった読み込みを捨てる仕組み（`operation-overlap.ts`）は、巻き戻りを防ぐためにはもう要らない。番号で比べれば、重なった読み込みが古ければ捨てられ、新しければ使える。Issue #54 で `operation-overlap.ts` を消し、重なった読み込みも番号で比べるようにした（捨てると、その間の別の端末の変更を同期メッセージで受け取れていない画面が古いまま残るため）。

## Considered Options

- 同じ時刻のスナップショットを古いとみなす（`<=` で比べる）: 同じ変更が HTTP と同期メッセージで2回届いたときに2回目を捨てるだけなら困らないが、時刻の同じ別の変更のあとのほうを捨ててしまい、画面が追いつかなくなる
- 記録の中身（操作イベントや記入の数）から新旧を決める: 進め方の変更や閉じたことも数えることになり、何を数えるかの規則を記録先ごとに持つことになる。数え漏れがあれば巻き戻る
- UserDO の時計を、処理するたびに前の時刻より 1ms 以上進める: サーバーの時刻を時計のずれの測定に使っているので、実時間からずらしたくない。端末の記録先にも同じ工夫が要る
- 番号をトリガーではなく、書き込みの契約（`saveStartedSession` など）の実装の中で進める: 書き込みの経路を足したときに進め忘れても気づけない
